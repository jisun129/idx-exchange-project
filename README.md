# California Housing Price Prediction

A regression project that predicts the final sale price (`ClosePrice`) of single-family
residential properties using CRMLS (California Regional MLS) sold-listing data. The project
has two parts that share the same preprocessing logic but serve different purposes:

- **`notebooks/`** - the research process: explores the data and compares five models
  (Linear Regression, Decision Tree, Random Forest, XGBoost, LightGBM) to figure out what
  works.
- **`src/` + `app_full.py`** - the production pipeline: reproduces that same preprocessing,
  but trains and serves **only LightGBM** (the model the notebooks' comparison settled on),
  for the actual price-prediction app.

See Section 4 for how these two halves relate, and which one to use for what.

## 2. Raw Data Is Not Included in This Repository

The raw CRMLS CSV files (`CRMLSSold*.csv`, meant to live in `data/raw/`) are **intentionally
excluded from version control** (see `.gitignore`) under this project's data non-disclosure
policy - CRMLS listing data cannot be redistributed publicly. `data/processed/` is likewise
excluded, since it's just derived output that's regenerated from the raw data.

This means:
- Anyone cloning this repository will **not** have `data/raw/` or `data/processed/`
  populated, and running `src/preprocess.py` or any notebook from 01 onward will fail until
  they supply their own copy of the CRMLS sold-listing data in that folder.
- The folder structure, all path defaults, and every notebook/script in this repo are
  written **assuming that data exists** at `data/raw/CRMLSSold*.csv` - nothing here works
  standalone without it.
- `models/` is the one exception: it's committed specifically so the app (`app_full.py`)
  works out of the box for anyone who clones the repo, without needing the raw data at all
  (see Section 6.3).

If you do have access to the raw data, place the monthly `CRMLSSold*.csv` files in
`data/raw/` and everything else in this README will work as documented.

## 3. Dataset

- **Source**: CRMLS (California Regional MLS) monthly sold-listing data
- **Date range used**: `CRMLSSold{YYYYMM}.csv` files from **2025-05 through 2026-05**
  (`start`/`end` in `01_exploration.ipynb`, matched by `--start`/`--end` in
  `src/preprocess.py`, default `"202505"`/`"202605"`). A file whose name doesn't match this
  exact `CRMLSSoldYYYYMM.csv` pattern in that range (e.g. a `..._filled.csv` or a multi-month
  export) is silently skipped by both the notebook and the script - this is intentional, not
  a bug, and keeps the two in sync (see `src/preprocess.py`'s docstring for detail).
- **Filter applied**: `PropertyType == "Residential"`, `PropertySubType == "SingleFamilyResidence"`
  (141,997 rows after filtering)
- **Target**: `ClosePrice` (final sale price)
- **Key raw features**: `LivingArea`, `BedroomsTotal`, `BathroomsTotalInteger`, `LotSizeArea`,
  `YearBuilt`, `AssociationFee`, `Flooring`, `PostalCode`, etc.
- **Supplementary data**: school district boundaries -
  [CA School District Areas 2024-25](https://data.ca.gov/dataset/california-school-district-areas-2024-25)
  (data.ca.gov, GeoJSON) - downloaded automatically, with retries and local caching (see
  Section 6.1)
- Column-level descriptions and keep/drop decisions are documented in `columns.xlsx`.

## 4. Notebooks vs. Production Pipeline - How They Relate

Both halves of this project implement the **same** preprocessing (Section 5): missing-value
handling, train-only outlier IQR bounds, and the 28-feature Week-6 engineering
(`BedBathRatio`, `PropertyAge`, `SchoolDistrictGIS`, `AreaComps*`). Where they diverge is what
happens after that:

| | `notebooks/` | `src/` + `app_full.py` |
|---|---|---|
| **Purpose** | Research: try things, compare models, decide what's best | Production: reproduce that decision reliably, serve predictions |
| **Models trained** | All 5 - Linear Regression, Decision Tree, Random Forest, XGBoost, **and** LightGBM | **LightGBM only** |
| **How hyperparameters are chosen** | Searched via walk-forward CV (`06_evaluation.ipynb`) | **Not searched** - the winning LightGBM hyperparameters from `06_evaluation.ipynb` are hardcoded as constants in `src/train_model.py` |
| **Output** | CSVs of metrics/comparisons, for humans to read | `models/price_model.pkl`, a single fitted object the app loads directly |
| **Run how often** | Once, to do the analysis (already done - see Section 8 for the results) | `src/preprocess.py` + `src/train_model.py` only when the deployed model needs refreshing (new raw data, etc.) |

`06_evaluation.ipynb`'s comparison found XGBoost and LightGBM statistically tied (MdAPE
within 0.05 percentage points, R² within 0.001) - see Section 8. **LightGBM was chosen for
the deployed model** for its lower fold-to-fold RMSE variance during tuning, a mild edge in
stability. This was a judgment call made when building `src/train_model.py`, not something
the notebooks' comparison uniquely forces - if you'd rather deploy XGBoost instead, swap
`LGBMRegressor` for `XGBRegressor` in `src/train_model.py` and use the XGBoost hyperparameters
from Section 8 below.

**In short: the notebooks explain *why* LightGBM was picked; `src/` and `app_full.py` are
*only* about LightGBM, running that decision in production.**

## 5. Preprocessing Summary (`02_preprocessing.ipynb` / `src/preprocess.py`)

Both the notebook and the production script apply the same steps, in this order:

1. **Drop rows with missing/invalid target**: rows with missing `ClosePrice` or
   `ClosePrice <= 0` are removed.
2. **Missing-value handling**: columns with more than 50% missing values are dropped
   (`MISSING_DROP_THRESHOLD = 0.5`); the rest are imputed (median for numeric, most-frequent
   for categorical), with `SimpleImputer(add_indicator=True)` also adding a flag column
   marking which rows were originally missing.
3. **Column-specific fixes**
   - `AssociationFee`: missing values filled with 0 (both NaN and 0 represent "no HOA" in
     this dataset).
   - `Flooring`: **not** used directly as a model feature - it's a multi-label column (e.g.
     `"Carpet,Tile,Wood"`) and is dropped from the feature set. Before being dropped, it's
     used to derive two summary features that *are* kept: `premium_score` (a 0-1 score based
     on the material mix) and `grade` (a categorical bucket - "Likely Premium" / "Likely
     Budget" / "Mixed/Mid-range" / "Unknown" - derived from `premium_score`).
4. **Leakage / unnecessary column removal**: IDs, URLs, photos, agent info, date strings,
   near-unique address-like columns, and very-high-cardinality categorical columns (`City`,
   `PostalCode` as a raw feature, etc.) are excluded. Fully-duplicate rows are also dropped
   at this point.
5. **Time-based train/test split**: the most recent month is fixed as the test set, and the
   preceding N months (N ∈ {3, 6, 9, 12}) are used as the training window - the N with the
   lowest RMSE is selected (see Section 6.1).
6. **Outlier handling** (train-only, log1p-space IQR with Tukey `k=1.5`):
   - `ClosePrice`: rows outside the train-only IQR bounds ($184,446 – $4,777,794) are
     **dropped**, but only within the training window - test rows are always kept as-is.
   - `LivingArea` / `LotSizeSquareFeet`: **clipped** (winsorized) to the train-only bounds,
     applied everywhere.
7. **Feature engineering**
   - `BedBathRatio` = bedroom count / bathroom count
   - `PropertyAge` = sale year − `YearBuilt`
   - `SchoolDistrictGIS`: each property's latitude/longitude spatially joined against CA
     school district boundaries to assign a district label. Only the top 30 districts (by
     frequency in the training data) are kept; the rest are bucketed into `"Other"`.
   - **Area-level trailing comps**: for each `PostalCode`, the median/mean price-per-sqft of
     sales over the 3 months immediately *before* that sale's own month
     (`AreaCompsMedianPricePerSqFt`, `AreaCompsMeanPricePerSqFt`, `AreaCompsSalesCount`).
     Built causally (`shift(1)` + rolling window before use) so a row's own sale is never
     part of its own comp.
   - The raw `Latitude`/`Longitude` coordinates are excluded from the model inputs (to
     prevent the coordinates themselves from dominating the model).
   - With these features added, the final feature set grows from 22 raw columns (14 numeric +
     8 categorical) to 28 raw columns (19 numeric + 9 categorical).
8. **Preprocessing pipeline**: numeric (median impute + StandardScaler), categorical
   (most-frequent impute + OneHotEncoder) - `fit` only on the training set, `transform` only
   on the test set (or, for the deployed model, on whatever a user submits via `app_full.py`),
   to avoid data leakage.
9. **Output**: 138,859 rows total for the selected 13-month range, split 126,835 train /
   12,024 test after outlier removal (`02_preprocessing.ipynb` writes this as one
   120-column `cleaned_preprocessed_data.csv` with a `split` column; `src/preprocess.py`
   writes only the 126,835 train rows, unencoded, to `model_ready_data.csv` - see Section 6.1).

## 6. Production Pipeline (`src/` + `app_full.py`)

### 6.1 `src/preprocess.py`

Reproduces `01_exploration.ipynb` + `02_preprocessing.ipynb` (Section 5's steps) as a single,
path-independent script:

1. Merges the raw monthly CSVs matching `[--start, --end]` (default `202505`-`202605`),
   filters to Residential/SingleFamilyResidence.
2. Drops fully-duplicate rows, cleans the target, fills `AssociationFee` NaNs with 0, derives
   `premium_score`/`grade` from `Flooring`.
3. **Picks the best training-window length** (3/6/9/12 months before the most recent month)
   by RMSE, exactly like `02_preprocessing.ipynb` Section 6-7.
4. Applies **train-only** outlier handling (log1p-space IQR, `k=1.5`): drops `ClosePrice`
   outlier rows from the training window only, clips `LivingArea`/`LotSizeSquareFeet`
   everywhere.
5. Builds the 28-feature Week-6 set, including the `SchoolDistrictGIS` spatial join (with
   automatic retries and local caching to `data/raw/CA_School_District_Areas_2024-25.geojson`
   - see the script's docstring) and the causal `AreaComps*` trailing comps.
6. Writes `data/processed/model_ready_data.csv` - the 28 features + `ClosePrice` for the
   **selected training window only** (126,835 rows - not every month in `data/raw/`).

```bash
python src/preprocess.py
# or, to override defaults:
python src/preprocess.py --raw-dir data/raw --output-dir data/processed --start 202505 --end 202605
```

### 6.2 `src/train_model.py`

Fits the final LightGBM pipeline on `data/processed/model_ready_data.csv`, using the
hyperparameters `06_evaluation.ipynb` found best via walk-forward CV (hardcoded as
`LGBM_BEST_PARAMS`, not re-searched here). Saves the fitted pipeline and three small lookup
files (feature medians/modes, valid school districts, valid `Levels` values - used to prefill
and populate the app's form) to `models/`.

```bash
python src/train_model.py
```

Run this (after `src/preprocess.py`) whenever the deployed model needs refreshing - e.g. once
a new month of raw data is available.

### 6.3 `models/` - Why It's Committed

Unlike `data/raw/` and `data/processed/`, **`models/` is committed to the repository on
purpose**. `app_full.py` only ever *loads* `models/price_model.pkl` - it never retrains
anything itself. That means:

- Anyone who clones this repo gets a working prediction app immediately, without needing the
  raw CRMLS data (which they likely don't have access to, per Section 2) or running the
  pipeline themselves.
- `src/preprocess.py` + `src/train_model.py` only need to be re-run by someone who *does*
  have the raw data and wants to refresh `models/` with newer predictions - after which the
  updated `models/` files get committed like any other change.

### 6.4 `app_full.py`

The Streamlit prediction app. Takes all 28 model features as input (grouped into Basic Info /
Lot & Structure / Amenities / Location & Quality / Market Context), pre-filled with
training-data medians/modes so only the fields you actually know need changing.
`BedBathRatio`/`PropertyAge` are computed automatically from simpler inputs (Beds, Baths, Year
Built) rather than asked for directly.

```bash
pip install -r requirements.txt
streamlit run app_full.py
```

It loads `models/price_model.pkl` and the three JSON lookup files next to it - if those are
missing (e.g. `models/` wasn't included when you cloned, or got `.gitignore`'d by mistake),
it shows an error telling you to run `src/preprocess.py` + `src/train_model.py` first.

## 8. Model Comparison Results (from `06_evaluation.ipynb`)

Overall test-set performance, retrained on the full training window with the best
walk-forward-CV hyperparameters:

| Model | R² | MAE ($) | RMSE ($) | MAPE (%) | MdAPE (%) |
|---|---|---|---|---|---|
| **LightGBM (tuned)** \* | 0.404 | 237,801 | 1,295,490 | 16.74 | **9.17** |
| XGBoost (tuned) | 0.405 | 237,625 | 1,294,507 | 16.92 | 9.22 |
| Random Forest (tuned) | 0.377 | 249,359 | 1,324,845 | 17.19 | 9.28 |
| Decision Tree (tuned) | 0.368 | 282,699 | 1,334,262 | 19.95 | 11.61 |
| Linear Regression | 0.316 | 306,216 | 1,387,910 | 23.84 | 13.55 |

\* **The model this project deploys** (Section 4).

- **Best hyperparameters**:
  - LightGBM (deployed): `{max_depth: 7, num_leaves: 63, learning_rate: 0.1, n_estimators: 400, min_child_samples: 10}`
  - XGBoost: `{max_depth: 7, learning_rate: 0.1, n_estimators: 400, min_child_weight: 1, subsample: 0.8}`
  - Random Forest: `{max_depth: None, n_estimators: 400, min_samples_leaf: 1, max_features: 0.5}`
  - Decision Tree: `{max_depth: None, min_samples_leaf: 10}`
- **LightGBM and XGBoost are effectively tied** for best overall (MdAPE within 0.05
  percentage points, R² within 0.001) - Section 4 explains why LightGBM, specifically, was
  picked for deployment.
- **Random Forest closes most of the gap** to the boosted models once `max_features=0.5` is
  tuned in, but still trails by roughly 0.1 percentage points of MdAPE.
- **Decision Tree and Linear Regression remain the weakest** models by every metric - a
  single tree still overfits even after tuning `min_samples_leaf`, and Linear Regression
  can't capture the non-linear pricing patterns the tree-based models pick up.

**Price-band breakdown** (5 quintiles of test-set `ClosePrice`):

- MdAPE for LightGBM/XGBoost is mildly **U-shaped**: ~8.5% in the cheapest quintile, dropping
  to ~7.2% in the second quintile, then climbing back up to ~13% in the most expensive
  quintile (≥ $1.69M). So relative error does concentrate somewhat at the high-price tail, but
  far less dramatically than raw RMSE numbers would suggest.
- R² computed *within* a narrow price band is unreliable and often strongly negative even for
  the best models - restricting the price range shrinks the variance in the denominator,
  exaggerating R² swings from the same absolute errors. MAPE/MdAPE (per-row percentage
  ratios) don't have this problem and are the metrics to trust for band-level comparisons.

**Conclusion**: LightGBM and XGBoost are the recommended models from this comparison, with
very similar accuracy overall and across price bands (LightGBM is the one actually deployed -
Section 4). Their main remaining weakness is concentrated in the top ~20% of listings by
price, where dollar errors are large in absolute terms even though relative (percentage)
error only degrades modestly.

## 10. Notes / Limitations

- The test set used for evaluation (Section 8) is always a single "most recent month," so
  sample size is limited and results can be sensitive to that month's market conditions.
- `ClosePrice` is heavily right-skewed; every model here predicts `log1p(ClosePrice)`, with
  predictions back-transformed (`expm1`) before scoring or display - this substantially
  improved model stability and test performance versus predicting the raw price directly.
- R² computed within a narrow price band is misleading (Section 8) because the reduced
  variance in the denominator exaggerates R² swings for the same absolute error - per-band
  comparisons should be read using MAPE/MdAPE rather than R².
- Model accuracy degrades somewhat for the highest-priced listings (top quintile) - worth
  keeping in mind if this is used for pricing decisions on luxury properties specifically.
- `SchoolDistrictGIS` depends on successfully fetching the CA school-district GeoJSON at
  least once (Section 6.1). If that download never succeeds and no local/cached file is
  provided, this feature falls back to `"Unknown"` for every row, meaningfully weakening that
  one feature (the other 27 are unaffected).
